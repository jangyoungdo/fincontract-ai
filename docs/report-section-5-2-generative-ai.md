## 5-2. 생성형 AI 모델 적용 방안

본 서비스는 생성형 AI가 계약의 위험 여부를 단독으로 결정하는 구조가 아니라, 개발 단계와 서비스 운영 단계에서 모델의 역할을 분리하고 각 결과를 결정론적 코드로 통제하는 구조로 설계하였다. 개발 단계에서는 Claude Code와 Codex를 AI 코딩 에이전트로 활용하였다. 도메인 담당자가 법령·판례 검토를 바탕으로 위험 유형, 정상 예외, 기대 탐지 결과를 정의하면, 두 에이전트가 이를 규칙 엔진, 검색 파이프라인, 자동 테스트와 기술 문서로 구체화하였다. 이 과정의 핵심은 AI가 임의로 기능을 만드는 것이 아니라 도메인 지식을 실행 가능한 명세와 회귀 테스트로 전환하는 데 있다. 변경사항은 기능별 브랜치와 Git worktree로 분리하고, Pull Request와 GitHub Actions를 통해 백엔드·프런트엔드 테스트, 빌드, 의존성 및 민감정보 검사를 통과한 경우에만 `main`에 반영하였다. 이를 통해 팀 구성원의 개발 숙련도 차이를 보완하면서도 AI가 생성한 코드의 변경 이력과 검증 근거를 남길 수 있었다.

서비스 운영 단계에서는 먼저 생성형 AI에 의존하지 않는 결정론적 분석 기준선을 실행한다. 업로드된 PDF·DOCX·TXT 파일은 형식과 크기를 검사한 뒤 서버 내부에서 텍스트를 추출하고, 개인정보를 마스킹한 후 조항 단위로 분리한다. Rule Engine 0.5.0은 「약관의 규제에 관한 법률」 제6조부터 제11조 및 제14조를 법적 근거 후보로 참조하는 19개의 실험적 검토 유형을 적용해 `findings[]`를 생성한다. 이 결과는 생성형 AI가 생성·수정·삭제할 수 없다. 예를 들어 Test 10에서 확인된 정상 변경 조항의 오탐을 줄이기 위해 R04에는 ‘사전 개별 통지’, ‘고객의 실질적인 거절 또는 계약 종료권’, ‘변경의 장래 적용’이 위험 표현 주변에 모두 존재할 때만 작동하는 복합 예외 게이트를 추가하였다. 반대로 Test 11에서 놓쳤던 ‘계속 사용하면 새 조건에 동의’, ‘일정 시간 무응답이면 수용 확정’, ‘계속 거래하면 계약상 지위 이전을 승인’과 같은 표현은 R11 의미 패턴으로 보강하였다.

규칙 엔진이 놓칠 수 있는 우회 표현은 EC2 내부에서 구동하는 `intfloat/multilingual-e5-small`이 보완한다. 이 모델은 문장을 생성하는 생성형 AI가 아니라 문장의 의미적 유사도를 수치화하는 오프라인 임베딩 모델이다. 고정한 모델 리비전과 가중치 해시를 사용하며, 규칙이 이미 탐지한 유형과 중복되지 않는 후보만 `candidate_findings[]`에 추가한다. 따라서 사용자 화면에서도 결정론적으로 탐지된 ‘검토 신호’와 의미 유사도로 찾은 ‘추가 의미 검토 후보’가 분리된다. 의미 후보는 자동으로 결정론적 신호로 승격되지 않으며 최종적인 법률 판단으로도 사용되지 않는다.

의미 후보의 정밀도를 높이기 위해 법률 근거 검색과 분리된 내부 판단 RAG를 추가하였다. 별도의 ChromaDB `decision_cards` 컬렉션에는 테스트 계약서 원문이 아니라 일반화한 합성 위험 패턴과 정상 예외 패턴만 저장한다. 후보 조항마다 위험 카드와 예외 카드를 검색한 뒤 ‘벡터 유사도 60% + BM25 키워드 일치도 20% + 판단요소 충족도 20%’로 점수를 계산한다. 위험 점수가 0.70 이상이고 정상 예외와의 차이가 0.08 이상이며 핵심 판단요소가 두 개 이상 확인되면 내부적으로 위험 패턴 우세로 본다. 정상 예외 카드의 필수 요소가 모두 충족된 경우에만 해당 의미 후보를 사용자 결과에서 제외한다. 검색 모델이나 ChromaDB에 장애가 발생하거나 판단 자료가 부족하면 후보를 삭제하지 않고 기존 결과를 유지하는 fail-open 정책을 사용한다. 판단 카드, 검색 점수, 판정 상태와 카드 버전은 내부 평가와 원문 없는 운영 지표에서만 확인하며 사용자 화면·PDF·공개 API 또는 법적 근거에는 노출하지 않는다.

법률 근거 RAG는 내부 판단 RAG와 목적과 데이터가 다르다. ChromaDB에는 법령, 공정거래위원회 심결, 법원 판례, 분쟁조정 사례, 조항 패턴을 구분하는 5개 법률 컬렉션 구조가 구현되어 있다. 각 마스킹 조항을 질의로 사용하고 벡터 점수 45%, BM25 점수 40%, 출처 권위 점수 15%를 결합해 상위 3개의 근거 후보를 선택한다. 다만 현재 출처 URL, 기준일과 SHA-256 해시까지 검증하여 실제 적재한 공개 코퍼스는 「약관의 규제에 관한 법률」 7개 조문이다. 공정위 심결·법원 판례·분쟁조정 자료는 개별 출처와 라이선스, 재배포 가능성을 확인한 뒤 단계적으로 확대할 예정이다. 따라서 5개 컬렉션의 검색 구조가 구현되었다는 사실과 5개 종류의 공식 자료가 모두 확보되었다는 주장을 구분한다. 또한 합성 `decision_cards`는 공식 법률 자료와 별도 컬렉션에 저장하며 법적 근거 후보로 인용하지 않는다.

운영 단계의 생성형 AI는 OpenAI Responses API이며 기본 모델은 `gpt-5.6-luna`이다. 현재 OpenAI는 두 가지 선택적 역할을 수행한다. 첫째, 19개 규칙과 로컬 E5가 포착하지 못한 표현이 있는지 마스킹된 분석 조항을 문서 단위로 한 차례 검토하고, 폐쇄형 R01~R19 taxonomy 안에서 추가 의미 후보만 제안한다. 모델이 반환한 `section_id`와 `rule_id`가 실제 입력과 일치하고, `evidence_quote`가 해당 마스킹 조항에 존재하는 정확한 연속 문자열이며, 동일 조항·동일 유형의 기존 신호가 없는 경우에만 후보를 채택한다. 둘째, 확정된 검토 신호와 추가 의미 후보의 구조화된 요약 정보를 바탕으로 사용자가 먼저 읽을 핵심 문장 2~3개를 생성한다. `gpt-5.6-terra`는 복잡한 재검토를 위한 deep 등급 설정으로 남아 있지만 현재 기본 운영 흐름에서 자동 호출하지 않는다.

OpenAI의 역할은 법률 근거 검색을 대신하거나 계약의 적법성을 판정하는 것이 아니다. 조항별 상위 법률 근거의 검색·정렬·부착은 애플리케이션 코드가 결정론적으로 수행한다. 모든 Responses API 요청은 JSON Schema 기반 Structured Outputs로 제한하며, 출력 형식과 ID, 인용문, 금지된 법률 단정 표현을 다시 코드로 검사한다. 모델이 ‘위법하다’, ‘적법하다’, ‘무효이다’처럼 확정적인 결론을 포함하거나 허용되지 않은 ID와 인용문을 반환하면 결과를 채택하지 않는다. 즉, 생성형 AI는 검토 범위를 넓히고 설명을 읽기 쉽게 만드는 보조 계층이며, 규칙 결과와 공식 근거의 통제권은 애플리케이션에 남는다.

개인정보 보호도 외부 모델 호출 이전의 코드 기반 게이트로 구현하였다. 원본 파일 바이트와 마스킹 전 계약서 원문은 OpenAI로 전송하지 않는다. PII 마스킹을 통과한 최소 조항 또는 이미 구조화된 검토 결과만 전송하며, 외부 요청 직전 payload 전체에 대해 PII를 다시 검사한다. 모든 Responses API 요청에는 `store: false`를 지정하여 API 요청 저장 기능을 비활성화하였다. 이는 공급자의 모든 데이터 처리 가능성이 물리적으로 0이라는 의미가 아니므로, 보고서에서는 ‘OpenAI 서버에 데이터가 전혀 남지 않는다’고 단정하지 않는다. 외부 API 호출 실패, 호출 예산 소진, 스키마 오류 또는 검증 실패가 발생하면 결정론 결과는 그대로 보존하고, 요약은 기존 템플릿으로 대체하거나 결과 상태를 `needs_review`로 전환한다. 최종 결과 역시 법률적 유·무효 판정이 아니라 사용자가 확인해야 할 검토 신호와 질문으로 제공한다.

현재 전체 처리 흐름은 다음과 같다.

`문서 검증 → PII 마스킹 → 19개 규칙 → E5 의미 후보 → 내부 판단 RAG → 법률 근거 검색 → 선택적 OpenAI 문맥 검토·요약 → 사용자 검토`

구현 검증에서는 PR #18을 기준으로 백엔드 테스트 140개와 프런트엔드 테스트 10개가 통과하였고, 프런트엔드 빌드, 운영용 Docker Compose 설정, GitHub의 저장소 통합 검사·의존성 검사·히스토리 안전 검사도 모두 통과하였다. 기존 EC2 운영 구성에서는 합성 계약서를 이용해 OpenAI Structured Outputs와 `store: false` 적용을 확인하고, ngrok HTTPS 주소에서 업로드, 분석, 결과 조회, PDF 생성과 문서 삭제까지의 흐름을 검증하였다. 새 내부 판단 RAG는 Git `main` 반영과 자동 테스트를 완료했으며, EC2에서 최신 `main`을 pull한 뒤 Docker 이미지를 다시 빌드해야 실제 실행 환경 반영 여부를 최종 확인할 수 있다. 기존 01~11 평가 평균 90.3점은 Rule Engine 0.4.0 기준이므로 0.5.0의 성능으로 인용하지 않으며, 현재는 Test 10의 정상 변경 예외와 Test 11의 세 가지 의미형 동의 패턴에 대한 회귀 테스트 통과만 검증된 개선 결과로 제시한다.
