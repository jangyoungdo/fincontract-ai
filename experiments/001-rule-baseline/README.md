# 실험 001: 여신약관 규칙 엔진 기준선

## 실험 질문

은행 여신거래기본약관 형태의 조항에서 세 가지 위험 신호를 결정론적 규칙으로 재현 가능하게 선별할 수 있는가?

## 범위

- 사업자의 일방적 계약내용 변경
- 기한의 이익의 과도한 상실
- 고객에게 불리한 전속적 재판관할

위험 신호 후보를 찾는 실험이며 불공정성 또는 위법성을 확정하지 않습니다. 현재 데이터는 파이프라인 검증을 위한 합성 문장 12개이므로 측정값은 실제 성능의 근거로 사용할 수 없습니다.

## 가설과 성공 기준

- 양성·음성·경계 사례를 동일한 규칙 버전으로 반복 평가할 수 있다.
- 모든 탐지 결과가 규칙 ID, 버전, 일치 구간과 법적 근거 후보를 포함한다.
- 합성 스모크 데이터에서는 규칙별 precision, recall, F1이 모두 1.0이다.
- 실제 공개 문서로 만든 분리 평가셋에서는 목표치를 별도로 합의한다.

## 실행

저장소 루트에서 실행합니다.

```bash
python3 -m unittest discover -s backend/tests -p 'test_*.py'
python3 backend/scripts/evaluate_rule_baseline.py \
  backend/tests/fixtures/loan_terms_synthetic_v0_1.jsonl
```

평가 결과 파일이 필요하면 `--output`으로 경로를 지정합니다. 생성 결과는 실행 환경에 따른 산출물이므로 기본적으로 커밋하지 않습니다.

Windows/WSL2 인계 환경에서는 호스트 Python 대신 이미 빌드된 Backend 컨테이너를 사용합니다.

```bash
./scripts/run-baseline.sh
```

이 명령은 외부 LLM이 비활성화되었는지 먼저 확인하고 `output/runs/<run-id>/result.json`에
커밋, 데이터셋 hash, 규칙·provider·컨테이너 메타데이터와 지표를 기록합니다. 사례 원문과
로컬 비밀값은 기록하지 않습니다.

## 다음 단계

1. 대상 약관의 공개 출처와 이용 조건을 manifest로 검증합니다.
2. 규칙 작성에 사용하지 않은 문서로 전문가 검토 평가셋을 만듭니다.
3. 실험 A의 실제 기준선을 측정합니다.
4. 같은 출력 스키마로 실험 C(RAG + 단일 분석 에이전트)를 구현합니다.
5. A와 C의 품질, 검토시간, 비용을 비교한 후 추가 에이전트 필요성을 결정합니다.

실험 C부터는 [모델·토큰 라우팅 정책](../../docs/model-routing.md)을 적용하고, 모델 등급별 품질과 실제 사용 토큰을 함께 비교합니다.
